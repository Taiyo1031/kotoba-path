# 言語学習Webアプリ(個人テスト版)を0から作ってください

あなたは、複数のサブエージェントを使いながら、次の仕様のWebアプリを0から実装し、**GitHub Pagesで開ける状態まで**仕上げるエンジニアリングチームのリーダーです。この文書がすべての仕様です。不明点は後述の「判断ルール」に従い、確認を待たずに進めてください。

---

## 1. ゴール

- ブラウザだけで動く、**少数言語の学習アプリ**の個人テスト版を作る。作者本人が使い心地を試すためのもので、最初はユーザーを集める段階ではない。
- ただし将来、多くの人が簡単に楽しく使えるものにしたいので、構造とデザインは「公開できる品質」を目指す。
- 最初の対象言語はマレー語(`ms`)。**言語はコードに固定せず**、初回アンケートで選ぶ。データ上は任意の言語コードを扱える作りにする。
- 学習者の母語は日本語(`ja`)。UIは日本語/英語を切り替えられる(既定は日本語)。
- 最終的に、GitHub PagesのURLを開けば動く状態にする。

### 今回やらないこと
サーバー、ログイン(Googleログインを含む)、課金、アクセス解析、外部APIへの通信(ローカルLLM接続の準備を除く)、ネイティブアプリ化。

---

## 2. 前提と制約

- **サーバーなしの静的サイト**。データはすべてブラウザ内(IndexedDB)に保存し、JSON/CSVで書き出し・読み込みできる。
- **学習内容(単語・フレーズなど)の本物のデータは、あなたが作らない**。作者が別のチャットAIで生成して、アプリに取り込む。開発用のダミーデータ(fixtures)だけは、少量作ってよい。その場合は、ファイルとデータの両方に「開発用ダミー・内容の正確性は未検証」と明記し、`verified: false` にする。製品の既定コンテンツとして同梱しない(開発メニューからのみ読み込む)。
- 外部のフォントやCDNに依存しない(ビルド成果物だけで完結させる)。
- Duolingoなど既存サービスのアセット(キャラクター、画像、音)は使わない。オリジナルのデザインにする。
- コードの識別子は英語、コメントとドキュメントは日本語でよい。
- 既存のスキル(ローカルLLM「LM Studio」を使った開発環境のスキルなど)が使える場合は、ボイラープレートの下書き、ダミーデータ、翻訳の下書きなど**補助作業**に使ってよい。設計と最終的な品質の判断は、リーダーであるあなたが行う。

## 3. 進め方

### フェーズ
各フェーズの終わりに、ビルドとテストが通ることを確認してから次へ進む。

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| 0 | 計画。`docs/PLAN.md`、`CLAUDE.md`、`docs/DECISIONS.md` を作る。タスクをサブエージェントに割り当てる | 計画が書かれている |
| 1 | 土台。プロジェクト作成、型とzodスキーマ、IndexedDB、i18n、ルーティング、デザイントークン | ビルドが通り、空のページ遷移が動く |
| 2 | データの入出力。JSON/CSV、検証つきの取り込み、プロンプト生成画面 | ダミーデータを取り込んで書き出せる |
| 3 | 学習エンジン。日程計算、FSRS、出題の生成、各出題形式 | ステップを最後まで進められる |
| 4 | 画面とデザイン(PC版)。アニメーション、ゲーム要素、各ページ | 一通りの流れを通しで操作できる |
| 5 | スマホ対応(レスポンシブ)。タッチ操作 | 幅360〜430pxで全ページが使える |
| 6 | 公開準備。GitHub Actions、README、動作確認 | `npm run build` と `npm run preview` で動く |
| 7(任意) | ローカルLLM接続 | 5章の「LLM接続」を参照 |

**フェーズ1〜4はPC版を優先**する。ただし、レイアウトはCSS Gridとflexboxとrem単位で組み、後からスマホ対応しやすい構造にしておく(フェーズ5で仕上げる)。

### サブエージェントの分担(案。環境に合わせて調整してよい)
1. **設計担当**:型定義、zodスキーマ、JSON仕様書、ダミーデータ
2. **学習エンジン担当**:日程計算、FSRS、出題の生成、乱数、各出題形式のロジック
3. **UI担当**:ページ、コンポーネント、アニメーション、i18n、ゲーム要素
4. **データ入出力担当**:IndexedDB、JSON/CSV、検証、プロンプト生成、取り込み画面
5. **検証担当**:単体テスト、手動チェックリスト、ビルドと公開設定の確認

担当間の境界は、型定義(`src/types`)とzodスキーマにする。型を変えるときは設計担当が更新し、他の担当は従う。

### 作業のルール
- `CLAUDE.md` に、規約、コマンド、ディレクトリ構成、重要な設計判断を書き、更新し続ける。
- 判断したことは `docs/DECISIONS.md` に、日付・理由とともに1行ずつ記録する。
- 小さくコミットする(Gitを使える環境なら)。

## 4. 技術構成

- **Vite + React + TypeScript**(strictモード)
- ルーティング:**HashRouter**(GitHub Pagesでは、SPAのパス直打ちが404になるため)。Viteの `base` はリポジトリ名から設定できるようにする(環境変数)。
- 保存:**IndexedDB**(`idb` か `Dexie`)。`navigator.storage.persist()` を要求する。
- 検証:**zod**
- 状態管理:Zustand または軽量なContext(どちらでもよい。過剰な構成にしない)
- FSRS:**ts-fsrs**などのオープンソース実装を使う。ライセンスを確認して `docs/DECISIONS.md` に記録する。
- アニメーション:基本はCSS。必要な場合のみ軽量なライブラリを追加する。`prefers-reduced-motion` を尊重する。
- テスト:**Vitest**(単体)、必要なら Playwright(スモークテスト1〜2本)
- リンタ/フォーマッタ:ESLint + Prettier
- 公開:**GitHub Actions** でビルドし、GitHub Pagesへデプロイするワークフローを作る。

## 5. 画面(ルート)とデザイン

### ページ構成
大きな1ページにせず、次のようにページを分ける。

| ルート | 内容 |
|---|---|
| `/welcome` | 初回アンケート(ウィザード形式で複数ステップ) |
| `/` | ホーム。学習パス(単元の並び)、今日の分、連続日数、XP |
| `/unit/:id` | 単元の詳細。ステップ一覧、予定日、到達目標 |
| `/lesson/:unitId/:stepId` | レッスン(出題画面) |
| `/review` | 今日の復習(FSRSで期限が来たもの) |
| `/data` | データ管理。プロンプト生成、取り込み、書き出し(JSON/CSV)、バックアップ状況 |
| `/settings` | UI言語、1日の目標、学習日数/週、読み上げ、(将来)LLM接続 |
| `/debug` | 開発用。通常のナビゲーションには出さず、設定から隠しリンクで入る |

### 初回アンケート(`/welcome`)
聞くことは大まかにする。**言語、目的、いつまでにどのレベルまで**。1画面に1つずつ聞く。
- 言語:選択式(最初はマレー語のみ。言語リストは設定ファイルで追加できる)
- 目的:キーワードの選択(複数可。例:旅行、仕事、日常会話、現地の友人と話す、同世代と話す)+自由入力欄
- 期限と目標レベル:期限(日付)、目標レベル(「あいさつができる」「旅行で困らない」「日常会話の入口」など日本語の目安+内部のCEFR対応)、1日の学習時間
- 入力方式は、後で差し替えられるように、回答のデータ形式(`profile.goal`)と入力画面を分けて作る。将来は音声入力も入れたい。
- 回答後、「骨組みのプロンプト」を生成する画面へ進む(8章)。

### デザインの方針
- **楽しく、簡単に使える**ことを重視する。詰めすぎず、デザイントークン(色・余白・角丸・影・フォントサイズ)をCSS変数で定義して、後で調整しやすくする。
- 明るく親しみのある配色。ライト/ダークは、ライトだけ作ってよい(トークンで拡張できる構造にする)。
- キャラクター(マスコット)は、オリジナルの簡単なSVGで1つ作ってよい(任意。凝らない)。
- **軽いアニメーション**:
  - ページ遷移(フェード/スライド、150〜250ms)
  - カードのフリップ
  - 正解/不正解のフィードバック(正解は軽く跳ねる、不正解は小さく揺れる)
  - XPのカウントアップ、連続日数の炎のパルス、進捗バーの伸び
  - 単元完了の演出(軽い紙吹雪など。重くしない)
  - `prefers-reduced-motion` の設定時はアニメーションを無効化または最小化する。
- **PC版を先に仕上げる**。キーボード操作(Enterで確定、数字キーで4択、矢印キーなど)に対応する。
- **スマホ対応(フェーズ5)**:幅360〜430pxで全ページが使えること。下部タブのナビゲーション、タップしやすいボタン(最小44px)、並べ替えはタップで動かせること(ドラッグは任意)。

### ゲーム要素(暫定ルール。`src/config/game.ts` に定数でまとめる)
- XP:正解 +10、ステップ完了 +20、単元完了 +50
- 連続日数:その日に「1ステップ完了」または「復習を1日の目標数こなす」で加算。1日休むと途切れる(猶予などは入れない)
- 1日の目標:新出+復習の合計数(既定20、設定で変更可)
- 数値は暫定なので、設定ファイルだけ変えれば調整できるようにする。

## 6. 学習エンジン

### 6.1 構造
- **コース**(言語、目的、期限、目標レベル)→ **単元**(場面ごと、到達目標つき)→ **ステップ**(単元内の小さな練習)。
- ステップは**アプリが項目から自動で組み立てる**。AIが生成するのは素材(単語・フレーズ・例文・文法メモ)だけ。問題文・選択肢・出題順・ステップの構成は、すべてアプリ側で決める。

### 6.2 ステップの組み立て
単元の項目を、5項目ずつのバッチ(設定で変更可)に分け、バッチごとに次の順で並べる。
1. 新出(intro):見出し語、意味、音声、例文、関係のある単語のまとめ
2. 受容(recognize):4択(外国語→母語)
3. 産出(recall):入力、並べ替え、4択(母語→外国語)
4. 文脈(context):穴埋め、フレーズの穴あき(スロット)

最後に**単元まとめ**(unitTest):単元内の全項目を混ぜて出題する(混ぜて出すほうが遅延テストで有利という研究にもとづく)。誤答した項目は、まとめの最後に再出題する。

出題形式の決め方:新規は受容 → 学習中は産出 → 定着(FSRSの安定度が高い)は文脈・産出。**誤答したら、1段階易しい形式に戻して出し直す**。

### 6.3 復習(FSRS)
- 単語・フレーズごとにFSRSの状態を持ち、期限が来たものを `/review` と各レッスンに混ぜて出す。
- 評価の対応:誤答 → Again、正解だがヒント使用または遅い → Hard、正解 → Good、自己採点のフラッシュカードで「簡単」を選んだ場合のみ Easy。
- 1回のセッション内の想起は、1項目あたり合計5回前後で打ち切る(それ以上はセッション内で繰り返さず、日を分けた復習に回す)。

### 6.4 日程の自動計算と再計画
- 入力:残り日数、残り単元、1日の学習時間、1週間あたりの学習日数(既定6日)、今日の復習の件数。
- 計算(暫定の式。`src/engine/pacing.ts` に純粋関数として作り、テストを書く):
  - 残りの学習日数 = 期限までの日数のうち、学習日にあたる日
  - 残りの新出項目数 = 未着手の単元の項目数(中身がまだない単元は `itemEstimate`)+進行中の単元の未導入分
  - 1日の新出数 = `clamp(ceil(残りの新出項目数 / 残りの学習日数), 最小3, 上限)`。上限は、1日の学習時間と復習の件数から求める(1項目あたりの所要時間は設定値)。
- **セッションが終わるたびに再計算**する。
- 状態の判定:計画上の累積予定数と実績の差で、「順調」「遅れ」「前倒し」を出す。境界値は設定で変えられるようにする(既定:±10%、または±2日)。
- **遅れたとき**は、次の3案を計算して提示し、選ばせる。
  1. 期限を延ばす(新しい期限の日付を計算して表示)
  2. 任意の単元(`optional: true`)を減らす
  3. 1日の量を増やす(必要な1日の学習時間を表示)
- **前倒しのとき**は、次の単元を早めるか、弱点(誤答の多い項目)の復習を厚くする提案を出す。
- 期限が現実的でない目標(残りの項目数に対して日数が極端に短い)は、最初に警告する。

### 6.5 単元の解放
固定のロックにせず、**自由に先へ進める「ゆるいロック」**にする。まだ中身がない単元は開けず、「この単元の準備」ボタンで、プロンプト生成画面へ誘導する。

### 6.6 乱数と選択肢
- **シード付きの乱数**(mulberry32など)を使い、出題と選択肢の順序を再現できるようにする。セッションごとのシードを保存し、`/debug` で固定できるようにする。
- 4択の誤答の選び方(優先順):
  1. その項目の `rel`(関係)の単語(`confusable` → `antonym` → `synonym` → `related`の順)
  2. 同じ品詞・同じタグの単語
  3. 同じ単元の他の単語
  4. 既習の単語全体
- 選択肢の並びは毎回シャッフルする。正解の位置が偏らないようにする。

### 6.7 出題形式の仕様
| 形式 | 仕様 |
|---|---|
| intro | 見出し語・意味・読み・音声・例文。関係のある単語がある場合は、まとめて見せる |
| flashcard | 表→裏。自己採点(わからない/あいまい/わかった/簡単) |
| mcq | 外国語→母語、母語→外国語、音声→意味。4択。関係のある単語を選択肢に混ぜる |
| cloze | 例文の一部を穴にする。選択式と入力式 |
| typing | 意味を見て綴りを入力。大文字小文字は無視。1文字違いは「おしい」として扱い、ヒントを出す |
| tiles | 並べ替え(Duolingo風)。文を語に分けてタイルにする。ダミーのタイルを1〜2個混ぜる。複数の正解(`accepted`)を許す |
| match | 5組のペアつなぎ(外国語と意味) |
| listening | 音声→意味の選択、または書き取り。読み上げが使えるときのみ有効 |
| phrase-slot | スロット付きフレーズ(7.4)。既習の単語の中から、シードに従って穴を埋める |

答え合わせの後、その項目に紐づく**文法メモのヒント**と例文を下に表示する。

### 6.8 読み上げ(TTS)
- Web Speech APIで、対象言語の音声がある場合のみ使う。**機能検出**を行い、使えない場合は音声ボタンを隠す(音声前提の形式を出題から外す)。
- マレー語の音声が端末で使えるかは未確認。使えない端末でも、アプリ全体が問題なく動くこと。

## 7. データ仕様

### 7.1 方針
- 保存形式は**1つのJSON**(ZIPや独自の拡張子は使わない)。拡張子は `.json`。
- 内容はセクションに分ける:`meta` / `profile` / `plan` / `content` / `progress`。
- 母語の意味は**母語1言語だけ**入れる(UI言語とは別)。
- 型は `src/types`、検証は `src/schema`(zod)に置く。`docs/data-format.md` に仕様書を書き、JSON Schema(`public/schema/*.json`)も出力する。
- `format` と `version` を持たせ、将来のマイグレーション関数を作れる構造にする。

### 7.2 全体構造
```json
{
  "format": "lang-study-data",
  "version": 1,
  "meta": { "exportedAt": "ISO8601", "appVersion": "0.1.0" },
  "profile": {
    "uiLanguage": "ja",
    "nativeLanguage": "ja",
    "targetLanguage": "ms",
    "goal": {
      "purposeTags": ["travel"],
      "purposeText": "",
      "targetLevel": "A2",
      "deadline": "2027-03-31",
      "dailyMinutes": 20,
      "studyDaysPerWeek": 6
    }
  },
  "plan": {
    "units": [
      {
        "id": "u01",
        "title": "あいさつと自己紹介",
        "canDo": "名前と出身を伝えられる",
        "scenario": "初対面のあいさつ",
        "keywords": ["あいさつ", "名前", "出身"],
        "itemEstimate": 20,
        "optional": false,
        "plannedStart": "2026-11-15",
        "plannedEnd": "2026-11-20",
        "status": "planned"
      }
    ]
  },
  "content": {
    "units": {
      "u01": {
        "version": 1,
        "verified": false,
        "generatedBy": { "tool": "string", "at": "ISO8601" },
        "words": [],
        "phrases": [],
        "sentences": [],
        "grammarNotes": []
      }
    }
  },
  "progress": {
    "fsrs": {},
    "unitProgress": {},
    "xp": 0,
    "streak": { "days": 0, "lastStudyDate": null },
    "sessions": []
  }
}
```
- `plan.units[].status`:`planned`(骨組みのみ)/ `ready`(中身あり)/ `inProgress` / `done`
- `progress.sessions`(履歴ログ)は容量の上限を決める(例:直近N件のみ保持)。上限を超えたら古い順に畳む。

### 7.3 単語
```json
{
  "id": "ms:makan",
  "lemma": "makan",
  "pos": "verb",
  "reading": "",
  "meaning": ["食べる"],
  "tags": ["food"],
  "rel": [{ "type": "related", "id": "ms:minum" }],
  "uncertain": false,
  "note": ""
}
```
- **IDの規則**:`${言語コード}:${lemmaを小文字にしてスペースを-に}`。同じ綴りで別の語(同形異義)は `~2`, `~3` を付ける。
- `rel.type` は `synonym` / `antonym` / `confusable` / `related`。参照先のIDは、同じコース内に存在すること。
- `uncertain: true`(AIが確信を持てない項目)は、画面に「要確認」のバッジを出す。
- **取り込み時のID検証**:`id` が規則どおりでなければ、自動で正規化して、参照(`rel` など)も書き換え、警告として一覧に出す。

### 7.4 フレーズ(スロット付き)
```json
{
  "id": "ph:suka-fruit",
  "target": "Saya suka {fruit}.",
  "meaning": "私は{fruit}が好きです。",
  "slots": { "fruit": { "tag": "fruit" } },
  "fixed": false
}
```
- `fixed: true` は固定フレーズ(穴なし)。
- スロットの穴には、`tag` をもつ**既習の単語**の `lemma` と `meaning[0]` を差し込む。候補がないスロットのフレーズは出題しない。
- 日本語の助詞や語順がテンプレートと合う語だけを、候補にする(合わない語のタグは、プロンプト生成側の指示で分ける)。

### 7.5 例文と文法メモ
```json
{ "id": "se:001", "target": "Saya makan nasi.", "meaning": "私はご飯を食べます。", "wordIds": ["ms:makan"] }
```
```json
{ "id": "gn:me-prefix", "appliesTo": ["ms:makan"], "title": "動詞の接辞", "hint": "なぜこの形になるかの短い説明" }
```
- 文法メモは、`appliesTo` の項目の答え合わせの後に、ヒントとして表示する。

### 7.6 サイズ対策
- 重複せず、IDで参照する。
- 単元ごとに分けて持ち、使うときに読み込む。
- 学習履歴は内容と分けて持つ。

### 7.7 CSV
- 単語表の書き出し。列:`id, lemma, pos, reading, meaning, tags, rel`。UTF-8(BOMつき)で書き出し、Excelで文字化けしないようにする。

## 8. プロンプト生成と取り込み

### 8.1 プロンプト生成画面(`/data` と、アンケート後)
**2種類のプロンプト**を作る。

1. **骨組みプロンプト**:コース全体の骨組み(`plan.units`)を作らせる。
2. **単元プロンプト**:1つの単元の中身(`content.units[unitId]`)を作らせる。

各プロンプトは、プロフィール(言語、目的、期限、レベル)と単元の情報から**自動で組み立てる**。画面には、
- **「コピー」ボタン**(`navigator.clipboard`、失敗時はテキストを選択状態にする代替)
- **「ダウンロード」ボタン**(`.md`か`.txt`)
- プロンプトのプレビュー

を付ける。

### 8.2 プロンプトに必ず含める内容
- 役割(「語学教材の作成者」)と、出力は**JSONのみ**(前置きや解説は書かない。コードフェンスは付けてよい)
- 出力するJSONのスキーマ(フィールド名と型)と、**IDの規則**
- 件数の指定:骨組みは単元数の目安、単元は**1回15〜25項目**。多い単元は、AとBに分けて出すよう指示できる
- **スキーマは平らに保つ**(深い入れ子にしない)
- **確信がない語は入れない**。入れる場合は `uncertain: true` を付ける
- 対象言語は、標準的な表記と一般的な用法に限る(俗語や方言は、指定があるときのみ)
- 関係(`rel`)は、同じ単元内の単語どうしだけに付ける
- スロット付きフレーズは、`tag` が付いた単語が単元内に3つ以上あるときだけ作る
- 例文と文法メモは、各項目に短く付ける(文法メモは「なぜそうなるか」を1〜2文で)
- 母語は日本語で書く(`nativeLanguage` に従う)
- プロンプト末尾に、**出力の自己チェック項目**(IDの規則、参照先の存在、件数、JSONとして正しいこと)

プロンプトの文面は、テンプレート関数として `src/prompts/` にまとめ、テストする(必須要素が含まれること)。

### 8.3 取り込み画面
- 貼り付け欄とファイル選択の両方に対応する。
- 処理の流れ:貼り付けテキストからコードフェンスなどを除去 → JSONとして解析 → zodで検証 → IDの検証と正規化 → 参照先の存在確認 → 重複の検出 → プレビュー(件数、警告、エラー)→ 確定して保存。
- エラーは、**JSONのパス(例:`words[3].rel[0].id`)と理由**を一覧で表示する。部分的な成功(一部だけ取り込む)は、最初は入れず、全体を取り込むか拒否するかにする。
- 取り込んだ単元は `verified: false` にする。ユーザーが確認したら、ボタンで `verified: true` にできる。
- **同じ単元の再取り込み**:IDの規則が同じなので、既存の学習履歴(FSRS)を保持したまま、内容だけを置き換える。置き換え前に差分(追加・削除された項目)を表示する。

## 9. データ管理と保存

- すべての状態を**IndexedDB**に保存する(`localStorage` は設定の一部にしか使わない)。
- **書き出し**:JSON(全体)とCSV(単語表)。ファイル名に日付を入れる。
- **読み込み**:JSONの検証 → 「置き換え」または「統合」を選ばせる。`version` が古ければマイグレーションする。
- **バックアップの促し**:最終バックアップ日を `/data` とホームに表示する。7日以上たっていれば、目立つ案内を出す(Safariなどでは、一定期間そのサイトを開かないと保存データが消えることがあるため)。
- **データの削除(リセット)**:確認ダイアログを出す。

## 10. デバッグ機能(`/debug`)

通常のUIには出さず、設定から隠しリンクで入る。
- **仮想日付**:今日の日付を変えて、日程計算、FSRS、連続日数を検証できる。
- **ダミーデータの読み込み**(fixtures)と、全データのリセット。
- **乱数シードの固定**。
- 状態のインスペクタ:`profile`、`plan`、FSRSの状態、`sessions` をJSONで表示する。
- 日程計算の入力と出力の表示(式の途中経過)。

## 11. テストと品質基準

必須の単体テスト:
- IDの生成と正規化
- スキーマ検証(正常、異常、参照切れ、IDの規則違反)
- 日程計算(順調・遅れ・前倒し、境界、期限が短すぎる場合、3案の計算)
- 乱数の再現性(同じシードで同じ出題・同じ選択肢の並び)
- 誤答選択肢の選び方(優先順、重複しない、正解を含まない)
- スロット付きフレーズの展開(候補なしの場合)
- FSRSのラッパー(評価の対応)
- プロンプトテンプレート(必須要素の含有)
- 取り込み(コードフェンス除去、エラーのパス表示、再取り込みで履歴が残る)

品質基準:
- `npm run build`、`npm run lint`、`npm run test` がすべて通る。
- TypeScriptのエラーがない(strict)。
- `prefers-reduced-motion` を尊重している。
- 主要ページがキーボードだけで操作できる。
- コンソールにエラーが出ない。
- 画像や音声などの外部リソースに依存しない。

## 13. 判断ルール(未決事項の暫定値)

確認を待たずに進め、判断は `docs/DECISIONS.md` に記録する。設定で後から変えられる形にする。

- **アプリ名**:仮に「Kotoba Path」とする。1か所(設定ファイル)で変えられるようにする。
- **初回アンケートの入力方式**:最初はキーワード選択+自由入力。差し替え可能な構造にする。
- **XPや連続日数の数値、順調/遅れの境界**:5章と6章の暫定値を使う。
- **英語UI**:主要な画面(アンケート、ホーム、レッスン、データ、設定)は翻訳する。デバッグ画面は日本語のみでよい。
- **単元数の目安**:骨組みのプロンプトでは、期限までの学習日数と1日の量から、単元数を目安として計算して渡す(1単元15〜25項目を想定)。
- **1日の新出数の初期値**:10〜15項目(日程計算で上書きされる)。
- **わからないことが出てきたとき**:実装を止めず、最も単純で、後から変えやすい選択を採る。ただし、データ形式(7章)を変える必要が出たときだけは、設計担当が `docs/DECISIONS.md` に理由を書いてから変更し、最後の報告に必ず含める。

- 公開URL(または、手動で行う手順)
- 暫定値で決めた点の一覧
- 確認できなかった点(マレー語の読み上げ、ローカルLLM接続など)

フェーズ1で `LlmProvider` のインターフェース(`generate(prompt): Promise<string>`)だけを作る。フェーズ7で、設定ページに次を追加する。

- HTTPSのGitHub Pagesから `http://localhost` へつながるかは、ブラウザで挙動が異なる可能性がある。つながらない場合は、その旨を表示して、コピペ方式へ誘導する(未確認の項目として、最終報告に書く)
- 接続できた場合は、プロンプトの結果を取り込み画面と同じ検証に通す(生成結果は未検証として扱う)。
